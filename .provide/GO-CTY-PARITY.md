## Working agreement

- **All work lands on the single local branch `feat/go-cty-parity`.** Not one branch per issue — splitting the work across branches complicates the review.
- **Nothing is pushed and no PR is opened.** The branch stays local until the whole implementation is done.
- **Do not close issues automatically.** No `Closes #N` in commit messages.
- **An adversarial review happens after implementation, performed by someone other than the implementing agent.** Commit in coherent, self-describing increments so that review has something readable to work against.

## Verify before filing

Two of the five items in phase 1 turned out not to be gaps at all. Both were filed from reading go-cty — its CHANGELOG in one case, the shape of its source in the other — rather than from running pyvider:

- The three `Contains` / `Merge` / `element` "behavioural fixes" described bugs **go-cty** had. pyvider is an independent implementation and never had them.
- msgpack `±Inf` was filed because `codec.py` has no infinity branch. It does not need one; Python reaches the same bytes implicitly.

Meanwhile the sweep that disproved them turned up a real bug nobody had listed (`contains` returning a definite `False` for partially-unknown collections).

**So: run the behaviour before believing the gap.** Absence of a code path in pyvider is not absence of the behaviour, and a go-cty bugfix is not evidence pyvider shares the bug. This applies directly to the remaining phases — several items in #14 were filed from grep results and should be re-checked empirically before any work starts on them.

## Phase 1 — correctness bugs

Wrong today. Verifiable with in-repo tests. No dependencies.

- [x] **#5 — stdlib functions silently drop marks**
  `functions/_marks.py` adds `@preserve_marks`, applied to all 68 exported functions. Collects marks deeply (matching go-cty's `UnmarkDeep`), calls the impl with unmarked arguments, re-applies the union to the result.
  Tests: `tests/functions/test_mark_propagation.py` — 119 cases, parametrized over every export, plus nested/deep cases and a fixture-completeness guard so a new export cannot skip coverage.
  Widened `CtyValue.with_marks` to `AbstractSet[Any]` (it always accepted frozensets; the annotation was too narrow) and dropped the now-redundant `type: ignore` in `object.py:129`.
  The decorator is the **seam** #12 fills in behind later.
- [x] **#15 — collection `validate()` discards marks on already-validated elements**
  Root cause was not the containers: they delegate to `self.element_type.validate(item)`, and the *element* type unwrapped `.value` and rebuilt a fresh `CtyValue`. `CtyObject` was the only type re-applying marks, by hand.
  `validation/marks.py` adds `@preserves_marks`, applied to all ten `validate` implementations outermost of `@with_recursion_detection`. Stated once, like `CtyType.unknown_marker`, rather than ten times. `CtyObject`'s hand-rolled copy deleted.
  Typed as an identity on the function type (`TypeVar` bound to `Callable`), so each `validate` keeps its own signature — a concrete signature flattens `CtyValue[str]` / `CtyValue[tuple[T, ...]]` / `CtyValue[Any]` together and shifts inference at every call site in the package.
  Tests: `tests/types/test_validate_preserves_marks.py`, 12 cases across every container and primitive. The `listval` workaround is gone from the #5 tests, which now use `validate()`.
- [x] **#16 — `cty_to_msgpack` silently drops marks instead of refusing to serialize**
  Found verifying #15. go-cty errors (`marshal.go:49`, "value has marks, so it cannot be serialized"); pyvider writes the value and discards the flag. Pre-existing, but #15 widens the exposure by making nested marks real.
  **Decision: match go-cty. Not blocked on #8.** Sensitivity reaches Terraform through `tfplugin6.Schema.Attribute.sensitive` (field 7), not through the value — `DynamicValue` carries only `msgpack`/`json` and has no mark channel. So no caller on this path needs `UnmarkDeepWithPaths` to comply.
  **Sequencing: the pyvider-side change must land first.** `pyvider/conversion/marshaler.py:118` applies schema marks and serializes on the next line, so those marks are already discarded; with a strict serializer it becomes a crash on every sensitive attribute. Remove that one call.
  **Do not remove `_apply_schema_marks_iterative` itself.** It has two other call sites — `plan_resource_change.py:237` and `apply_resource_change.py:268` — both *inbound*, after `unmarshal`. Marks cannot cross the wire, so the handlers re-derive them from the schema and hand the marked value to the resource as `ctx.config_cty`. `pyvider-components/tests/resources/test_tdd_resource_context_contract.py:139` is a live contract on that path.
  **Blast radius, from a full `/Volumes/data/pyv` sweep:** `pyvider` is the only production consumer that marks. `pyvider-components` reads marks in tests on the inbound path. `tofusoup`'s `*_with_marks` tests assert in memory and never serialize a marked value. Nothing else marks. One line of production code changes outside this repo.
  Breaking change for any other caller that marks and serializes: needs a release note, not a patch release.
- [x] **~~#14 item 9 — msgpack `±Inf` handling~~ — already correct**
  Filed because `codec.py` has no infinity branch. It does not need one: `float(Decimal("Infinity"))` is already `inf`, and msgpack encodes that as float64 infinity — byte for byte what go-cty's explicit `EncodeFloat64(math.Inf(...))` produces (`cb7ff0000000000000` / `cbfff0000000000000`). Go needed the special case; Python does not.
  Pinned with `tests/codec/test_msgpack_infinity.py` so the encoding cannot drift onto the large-number-as-string path.
- [x] **~~Split out of #9 — behavioural fixes to shipped functions~~ — not needed**
  All three were derived from go-cty's CHANGELOG rather than from running pyvider, and all three were already correct on `main`. pyvider's implementations are independent re-writes; they never had go-cty's specific bugs.
  - `Contains` with a null second argument — already accepted, finds null elements correctly
  - `Merge` on all-null args — already returns `{}` without raising
  - `element` negative index into a tuple — already returns the right element
  **Lesson for the rest of this work: test the behaviour before filing it as a gap.** A CHANGELOG entry describes a bug *go-cty* had, which says nothing about whether a separate implementation shares it.
- [x] **`contains` returned a definite `False` for partially-unknown collections**
  Found by the sweep above — not on any list. An unknown element could still be the value being searched for, so a miss is undecided rather than false. An exact match still wins outright. Mirrors go-cty's `ContainsFunc`.
  Same class as #5 and #15: claiming certainty that is not there.
- [x] **#17 — `MAX_VALIDATION_DEPTH` advertised a depth it could not deliver**
  **Closed.** Root cause measured, not guessed: validation costs exactly **two Python frames per level** (the `with_recursion_detection` wrapper, then the `validate` it wraps) — stack depth at the innermost leaf is `2 × levels + 2`. Against CPython's 1000-frame limit, 500 levels needs the entire stack with nothing left for the caller, so the real ceiling was **496** and input nested 497–500 deep returned a silent unknown from inside the documented limit.
  The limit is now **derived**: `(sys.getrecursionlimit() − VALIDATION_STACK_MARGIN) // FRAMES_PER_VALIDATION_LEVEL`, giving 480 at the default recursion limit — 480 promised, 480 delivered, verified by binary search. It tracks a raised recursion limit (3000 → 1480, also verified) and is pinnable via `PYVIDER_CTY_MAX_VALIDATION_DEPTH` through the existing `CtyConfig`/`env_field` pattern. Derived per context, so it follows a limit changed after import.
  The guard now stops *before* Python does, so exceeding the limit is a controlled unknown rather than a `RecursionError` thrown in the caller's stack. The attribution threshold for owning a `RecursionError` is taken from the live limit rather than its own constant, so the two cannot drift.
  Found while fixing it: **`pyvider.cty.context` declared a second `MAX_VALIDATION_DEPTH = 500`** that governed nothing — its depth mechanism (`deeper_validation`, `get_validation_depth`) has no callers in the validator, only its own tests — yet it was the constant the documentation pointed readers at. Two same-named constants that disagree is how the 500 came to be believed. Now re-exported from the real one.
  Four documentation files that promised a flat 500, one of them stating the limit was *not* runtime-configurable, corrected.
  Pre-existing, not a regression from this branch — verified against a clean `gh-origin/main` worktree before any of it was touched.
- [x] **Set elements carried marks; go-cty forbids that**
  `CtySet.validate` now deep-unmarks each element and hoists the union onto the set, as `SetVal` does (`cty/value_init.go:270`). go-cty goes further and panics on hashing a marked element (`cty/set_internals.go:39`) rather than trust the invariant to callers.
  Not cosmetic: de-duplication keys on the element's value, which is mark-blind, so a sensitive element colliding with an equal unmarked one was overwritten and its mark lost outright. **Behavioural change** — `set.value[i].marks` is now always empty and the marks are on the set.
- [x] **`equal` / `not_equal` decided comparisons they could not see**
  Same class as `contains`, found by sweeping for it after fixing that one. Both tested only top-level `is_unknown`, so an object with an unknown attribute reached `==` and got a plain bool: `equal(obj{a: unknown}, obj{a: "z"})` returned a definite `False` and `not_equal` a definite `True`, when that attribute could still resolve to `"z"`.
  Only objects were affected, and the reason is worth remembering: **containers are inconsistent about propagating element unknowns**. A list built from an unknown element reports itself unknown; an object with an unknown attribute does not. Anything reading `is_unknown` to decide whether a value is usable inherits that inconsistency.
  Swept the rest of the stdlib for the same shape. No other case found: the other `is_unknown` guards are conservative (unknown in, unknown out), `index` is index-by-key and matches go-cty's `IndexFunc`, and `distinct` on objects fails on hashability, which is a separate pre-existing limit.
- [x] **Three-valued equality — `CtyValue.equals()`, go-cty's `Value.Equals`**
  `==` returns a plain bool, so it must decide even when the data cannot support a decision. `equals()` can return unknown, and `contains`, `equal` and `not_equal` now all route through it instead of each carrying their own approximation.
  This replaces the earlier conservative stopgap, which called anything containing an unknown undecided. That was safe but needlessly vague: a known attribute that differs still rules a value out no matter what the unknown resolves to. `obj{a: unknown, b: "x"} == obj{a: "z", b: "DIFFERENT"}` is now a definite `False` where it used to be unknown, while `obj{a: unknown, b: "x"} == obj{a: "z", b: "x"}` stays correctly undecided.
  Covers the ordering go-cty is careful about — unknowns are examined *before* nulls, because an unrefined unknown may yet become null and nulls of any type are equal — plus mark propagation (compare unmarked, union onto the result, top-level-only marks when exactly one side is null), dynamic unwrapping, and structural recursion for list, tuple, set, map and object.
  **Not implemented**: go-cty disqualifies some comparisons early from an unknown's refinement bounds (`Value.Range().Includes`). pyvider.cty has only partial refinement support, so those return unknown here. Safe direction — vaguer, never wrong.
  `CtyValue.is_wholly_known()` (go-cty's `Value.IsWhollyKnown`) landed alongside it and remains the right test wherever a value has to be *usable*, as opposed to compared.
- [x] **`CtyList` refuses a null element, and refuses it on read** — *worklist #1, both halves closed 2026-08-16 — breaking*
  A null is a value of any type in cty and go-cty encodes one inside any container. This package refused two of them, and refused them on **read**: a provider handed state containing `["a", null]` for a `list(string)` raised `CtyListValidationError` from `cty_from_msgpack` instead of decoding it. `["a", null]` is valid Terraform configuration, so this was reachable from a practitioner's `.tf` file.
  The inconsistency is the tell, and it is the shape of every other bug this work has found — a rule applied to the container types someone had in mind. A null decodes fine inside a **map**, a **set** and a **tuple**. It was refused inside a **list**, and inside an **object** unless the attribute was declared optional. Both are now closed; only the byte-level set-ordering item below remains under this heading.
  Declaring an attribute optional was never a general workaround: optionality adds go-cty's third element to the wire type, so it changes the type Terraform is told about.
  Every container that reads a null back is pinned as *passing* in `tests/compatibility/test_tofusoup_compat.py::READS_A_NULL` — including the two that were strict xfails there until their guards came out. They stayed in the table rather than being deleted, because the next change to those code paths is exactly what they exist to catch.
  A fourth, separate and byte-level: a set holding a null re-encodes with the null first where go-cty writes it last. Both decode to the same value, so only a byte comparison catches it — and Terraform compares serialized state, so it is a diff that reappears on every plan. Set ordering agrees everywhere else; only a null moves it.
- [x] **`CtyObject` refuses a null for a non-optional attribute** — *closed 2026-08-16, `fadb4f6` here and `5fb7b13` in pyvider — breaking*
  `object.py:137-143`. Same class as the list guard, but it could not be removed unilaterally, and the investigation is worth not repeating.
  **`optional_attributes` was doing two jobs in one function**, and only one is go-cty's. Absent attribute → null (`object.py:115-119`) is exactly go-cty's documented semantic and stays. Present-but-null → raise was invented and has no counterpart anywhere in go-cty.
  **What Terraform actually does**, which settled it. Terraform keeps two types per schema: `ConfigType()` preserves optional attributes and decodes *configuration*; `ImpliedType()` is `specType().WithoutOptionalAttributesDeep()` and strips them recursively (`configschema/implied_type.go:129`). Everything crossing the provider protocol is marshalled with `ImpliedType()` — six call sites in `plugin6/grpc_provider.go`. So **the object type a provider receives has no optional attributes at all**, and Terraform sends nulls for those attributes constantly. Under this package's rule every one of them was "an attribute that cannot be null".
  pyvider survived only because it never decodes against the type Terraform advertises — it builds its own from its own schema (`schema/types/object.py:41`, `optional or computed`), which marks optional exactly where the data is null. A load-bearing coincidence, not a design.
  **The fix, in order.** `validate_config` does the check itself first — it has the schema, so it knows which attributes are `required`; cty does not and cannot. *Then* the guard came out here. Reverse order leaves a window where nothing checks.
  The check is `pyvider/schema/required.py`, and it **recurses**, because the guard it replaces applied at every depth: attributes, the nested schema `a_obj` keeps on the attribute, and nested blocks by nesting mode, carrying a `CtyPath` throughout. Two limits are structural rather than oversights, and are stated in the code so they are not mistaken for bugs. `a_list(a_obj(...))` and the other element factories take a `CtyType` and discard the `PvsAttribute` wrapper, so required-ness below a *collection attribute* is unrecoverable by construction. Set-nested blocks report the block and not an element: Terraform identifies a set element by value, `cty_path_to_proto_path` has no step for that, and an index there would be an invented position. Both raw Python and `CtyValue` payloads are handled — the one production caller, `validate_ephemeral_resource_config`, passes `config_cty.value`, whose attributes are `CtyValue`s, so a walk that only knew about `None` would have passed everything it was given.
  **The recorded blast radius was wrong in the half that mattered**, and the way it was wrong is the recurring one. It said 2 failures of 1421 in `pyvider`, "both testing one feature — `PvsSchema.validate_config()`". Only one of the two does. `test_tdd_deep_diagnostics.py:191` reaches *around* `validate_config` into `schema.block.to_cty_type().validate()`, so moving the check into `validate_config` would not have fixed it, and the plan as written would have been discovered incomplete at the point of running it. Its helper goes through `validate_config` now — the entry point a provider actually uses, and the only one that checks required-ness. The lesson is the same one this file keeps relearning: a blast radius counted by *how many tests fail* says nothing about *what they test*, and the difference is the whole plan.
  **Not needed**, recorded because it was proposed and is wrong: pyvider does not need Terraform's `ConfigType`/`ImpliedType` split. A provider never decodes HCL config — Terraform does that and sends msgpack — so pyvider only ever lives on the implied-type side. `conversion/utils.py:40` already uses `optional_attributes` correctly and none of the twelve `to_cty_type()` call sites need splitting.
  Verified against the oracle: the `object attribute` case moved from `STILL_REFUSED` into `READS_A_NULL` in `test_tofusoup_compat.py` and passes. cty 2073 passed / 5 xfailed with `--run-compat`; pyvider 1529 passed against the patched cty.
- [x] **`contains` on a null collection returns unknown; go-cty raises** — *closed 2026-08-16 as a side effect*
  `collection.go:340`, "cannot search a nil list or set". Deferred here as "a behavioural break that belongs with the strictness work", and that is exactly where it went: the framework null policy refuses argument 0 before `contains` runs. Both raise now, verified against the oracle. Worth noting as the argument *for* fixing a class rather than a case — nobody had to come back to this entry. Much weaker case than #16 — nothing leaks, the caller just gets a vaguer answer.
- [x] **Five stdlib functions answered differently from go-cty** — *breaking*
  Found by the oracle, not by reading: `regex`, `regexall`, `indent`, `flatten`, `chunklist`.
  - `regex`/`regexall` took `(string, pattern)` where go-cty takes `(pattern, string)`. Both are strings, so a call written for one order type-checks against the other and silently returns a wrong answer.
  - `regex` returned the whole match and discarded capture groups. go-cty's result type *is* the capture groups (`regexPatternResultType`): no groups → the whole match as a string; unnamed groups → a tuple in order; named groups → an object; mixing the two kinds → refused. A group that did not participate is null, not `""`.
  - `regex` returned `""` for a non-match where go-cty raises. `""` is a legitimate match for plenty of patterns, so the caller could not tell the two apart.
  - `indent` took a prefix *string* where go-cty takes a *count of spaces*, and indented the first line, which go-cty deliberately does not — the function exists to line a multi-line value up under something already on the first line. Deliberate divergence kept: a negative count raises cleanly rather than reproducing go-cty's `strings.Repeat` panic.
  - `flatten` returned a `list` with a unified element type where go-cty returns a `tuple`, which is why go-cty need not widen a mixture to dynamic. It also flattened one level where go-cty recurses, dropped null elements go-cty keeps, and raised on a non-sequence element go-cty passes through.
  - `chunklist` erased the chunk element type to dynamic (go-cty's return type is `cty.List(args[0].Type())`), and refused a size of 0 that go-cty reads as one chunk holding everything. Kept as a superset: a tuple argument is accepted, with its element types unified, where go-cty's `list(dynamic)` parameter refuses one outright.

  Zero callers anywhere in the workspace, so nothing broke — but all of it is a breaking API change for anyone outside it, and belongs in the same release as the other three.
  Now covered by `tests/compatibility/test_stdlib_oracle.py`, which compares **answers** rather than wire bytes: 27 calls agreeing on type and value, plus 5 that both implementations must refuse. That file is the thing that was missing. Every one of these divergences survived because every test asserted what the code did, so nothing could notice.

  Three pre-existing gaps surfaced while implementing them. None was fixed there; each is wider than that item.
  - [x] **`CtyObject.validate` refuses a null attribute** unless it is declared optional — *closed 2026-08-16 with worklist #1's object half, `fadb4f6`*. go-cty has no such rule — nullability is not part of an object type there. This was not hypothetical: a named capture group that does not participate in a match is null, so `regex("(?P<x>a)|(?P<y>z)", "a")` crashed until the result was built directly rather than through `validate`. That workaround is now unnecessary, though it is harmless and stays. Declaring the attributes optional was never the fix, because that adds go-cty's third wire element to the type.
  - [ ] **Python `re` is not RE2.** `regex(r"(a)\1", "aa")` and `regex("a(?=b)", "ab")` both succeed here and are *refused* by go-cty ("invalid escape sequence in \1", "invalid or unsupported Perl syntax in (?=").   - [x] **A `CtySet` cannot hold a list** ~~because a `CtyValue` with a list payload is unhashable~~ — *closed 2026-08-17 by the container-hashing work (`307ac08`)*: `__hash__` hashes the canonical sort key for containers, so `set(list(string))` validates, de-duplicates and round-trips. ### What the collapse was hiding

Closed 2026-08-17 in `8c3222a`, `fd32cc8`, `9889e42`. Recorded at length because the *shape* matters more than the eleven bugs: a value that cannot be constructed is a value nothing is tested against, and the collapse made the ordinary plan-time shape — a container holding an unknown element — unconstructible for a year.

**The original fault.** `list.py`, `map.py`, `set.py` and `tuple.py` each hoisted element unknown-ness onto the container; `object.py` never did, which is why this survived since 2025-07-25. Terraform resource schemas are objects at the top level, so the common case of an unknown *attribute* always round-tripped, and the loss needed a collection value to show itself. go-cty draws the line at `IsKnown` vs `IsWhollyKnown`, and this package *had* `is_wholly_known()` the whole time — `validate` was destroying the values it applies to.

**What came out when it was removed.** Every one of these was sound-but-vague before and actively wrong after, which is why they had to land in the same branch rather than be filed:

- `join` returned the string `'a-UNREFINED_UNKNOWN'` — a marker object's `repr`, headed for state.
- `jsonencode` returned `'["a", null]'`, encoding *unknown* as JSON **null**: a different value, not a different rendering.
- `zipmap` raised on an unknown key; `compact` kept an unknown because the marker is truthy, asserting it was definitely not `""`; `distinct` de-duplicated two unknowns into one.
- `sort` refused a list holding an unknown. go-cty *defers* — a same-length list of all-unknowns, since the ordering is undecided — and a **null** element is still an error. Treating the two alike is what hid it.
- `formatlist` left deferred rows as bare unknowns where go-cty refines them not-null: formatting always produces a string, so the row cannot be null whatever the argument becomes.
- **Sets could not hold two unknowns at all.** The payload was a `frozenset`, and two unknowns of one type are `__eq__`- and hash-equal, so the container itself was the constraint. go-cty's `set_internals.go` is explicit that two unknowns are never equivalent for set membership. `toset([a.id, b.id])` at plan time is two elements, and the count reaches Terraform. Payload is now an ordered tuple in canonical order (knowns sorted, then unknowns in supply order, then nulls) — which is what `CtySet` had always declared, `CtyType[tuple[T, ...]]`.
- `length` on a set then over-claimed, counting stored elements. An unknown may still resolve equal to another member, so the count is a *bound*: go-cty answers `[1, n]` and does not credit definitely-distinct knowns toward the lower bound.
- `_hoist_set_marks` rebuilt a set payload as a `frozenset`, silently re-collapsing what had just been fixed.
- **Refinements were destroyed twice over**: `validate` rebuilt every unknown bare, and `cty_from_msgpack` flattened every *nested* unknown because only the top level is rebuilt against the schema. Decoding go-cty's own bytes and re-encoding them turned `92 c7 05 0c 81 02 a2 68 74 a1 7a` into `92 d4 00 00 a1 7a`.

**The oracle was measuring the wrong population, twice.** `rich()` encodes the post-collapse value, so the msgpack case labelled *"an unknown inside a list"* was handing go-cty a wholly-unknown list and agreeing for the wrong reason. And `cty call` reported every unknown result as a bare `unknown: true`, so *every* unknown answer compared equal to every other — "both sides declined" was being read as "both sides agree" across 1331 cases. The harness now reports refinements alongside an unknown answer, and falls back to msgpack for a result `cty/json` refuses to marshal (a container holding an unknown), which is how `sort` and `formatlist` were caught. 548 existing cases already agreed on refinements, which is worth *knowing* rather than assuming.

**Deliberately not matched — and since 2026-08-17, not by leaving it alone either.** go-cty's `convert` of a **set whose length is unknown** to a **list** returns a wholly-unknown value typed from the *source* element type, not the target — `conversion_collection.go:16-22` short-circuits on `!val.Length().IsKnown()` and builds `cty.UnknownVal(cty.List(val.Type().ElementType()))`, leaving the target `ety` unused. Re-verified 2026-08-17, and the trigger is narrower than first recorded: the set's store must hold **more than one** element with at least one not wholly known (`value_ops.go:1133-1140` gives a single-element set an exact length), the source must not be *wholly* unknown (`conversion.go:36-47` handles that correctly, against the target), and the target must be a **list** — `conversionCollectionToSet` has no such short-circuit, and list→list, map→map, map→object, object→map, tuple→list and tuple→set all agree. It is a contract violation rather than a debatable treatment of unknowns because the wrong type propagates: `Convert(object({s=set(number)}), object({s=list(string)}))` yields a *known* object typed `object({s=list(number)})`, so a provider decoding config into its schema receives a value that does not conform to it. **But only half of go-cty's answer is wrong.** Its comment is right that a set store of `{1, unknown}` may coalesce to one element, so a definite-length list is not a correct answer either — and this library's elementwise conversion hardened its own `[1, n]` length bound into an exact `n`, which `length()` on the source and on the result openly contradicted. The strictly correct answer is neither side's: an *unknown* list of the **target** element type, refined `collection_length ∈ [1, storeLength]`.

**Implemented 2026-08-17, and the analysis above is the justification rather than an invitation to revisit it.** `convert` now returns exactly that third answer, and the reason to record the reasoning at this length is that all three answers look defensible in isolation: go-cty's is what the reference implementation does, the elementwise one is what type-correctness alone would suggest, and only reading the two together shows that each gives up the half the other keeps. `set(number){1, unknown}` to `list(string)` was a *known* `list(string)` holding `"1"` and an unknown, whose `length()` said `2` while the source's said `[1, 2]`; it is now an unknown `list(string)` refined `collection_length ∈ [1, 2]` and not-null, whose `length()` is the source's answer unchanged. Not-null is not a judgement call either — the source is a known, non-null set, so whatever the length turns out to be there is definitely a list. The enclosing case moves with it: `object({s=set(number)})` to `object({s=list(string)})` is still a *known* object of the type the caller asked for, with the one attribute deferred inside it, where go-cty hands back `object({s=list(number)})`.

The code is `conversion/explicit.py`, in the one collection branch: `_set_length_is_unknown` decides whether the store's count is a bound rather than a count — the same rule, and the same `_AMBIGUOUS_SET_SIZE`, that `length` already applies in `functions/collection_functions.py`, because a conversion reporting a length its own `length()` contradicts is the whole fault being fixed — and `_list_of_unknown_length` builds the result through `refine(...).not_null().collection_length_lower_bound(1).collection_length_upper_bound(store)`. Marks come off the set alone, which is not a shortcut: `CtySet.validate` hoists element marks onto the container as go-cty's `SetVal` does, so there are none left on the elements being dropped. Every boundary the entry names was re-run and is untouched — a wholly-unknown source still resolves against the target through the earlier interception, a single-element set still converts elementwise to a known one-element list, set→set still converts elementwise, and list→list, map→map, map→object, object→map, tuple→list and tuple→set still agree with go-cty. The full differential suite is green at 2310 passed with the twelve standing xfails, and the six tests in `tests/compatibility/test_conversion_oracle.py` now pin the fix and its three boundaries instead of the hardening; the sixth, whose docstring said it should turn red on a deliberate improvement, is that test re-pointed rather than deleted, and now asserts that `length()` gives the *same* refinement for the source and the result rather than naming the numbers.

Two consequences follow. The upstream report on `conversionCollectionToList` can now cite a working implementation rather than a proposal — deferral and the caller's type are not in tension, and a Go patch would be the same two lines building `cty.UnknownVal(cty.List(ety))` with a length refinement off `val.LengthInt()`. And **0.5.0's breaking-change list gained its forty-fourth entry** for it: `convert` from a set holding an unknown to a list returns an unknown where it used to return a value, which any consumer branching on `is_unknown` will notice. Written up in `CHANGELOG.md` as item 44, with the counts corrected here and the parity matrix's conversion entry updated to state the length refinement.

- [x] **#10 — `Refine` builder + consistency assertions** — *closed 2026-08-17, `b11177c`*

## Phase 7 — architecture

  **Every one of the four was an improvement on go-cty, and that is what made them divergences.** An unbounded number bound returned an unknown — which is what `NumberLowerBound`'s docstring promises and not what its code does, since it returns `cty.NegativeInfinity`. `includes()` answered `True` for a known value equal to the candidate; go-cty builds a *synthetic* range for a known value and never concludes membership from bounds, only exclusion, and its docstring says so. The undecided answer was a bare unknown where go-cty's carries a not-null refinement a caller can observe. And the type check used equality where go-cty uses `TestConformance` against the constraint, in a different order, so a dynamic-typed candidate against a concrete range answered "cannot say" instead of "no".

- [x] **#12 — the `cty/function` framework** — *closed 2026-08-17*

  7. `flatten` returns a tuple rather than a list, recurses through nested sequences, keeps null elements, and passes non-sequence elements through instead of raising. `chunklist` preserves the element type and accepts a size of 0.
  8. **`length` refuses a string.** It counted code points, which agreed with neither go-cty (which refuses the call, leaving strings to `strlen`) nor Terraform (which counts grapheme clusters — 1 for a four-person family emoji where this said 7). It now also accepts a dynamic wrapping a collection, which it previously refused; that half is a widening and breaks nobody. Callers wanting the old answer have `len(value.value)`; `strlen` is not available yet, since it needs the deferred UAX#29 decision.
  9. **`regexreplace` expands the replacement by Go's rules, not Python's.** The two dialects are inverses: Go reads `$1` and `${name}` and passes `\1` through as literal text; Python's `re.sub` does exactly the reverse. Every replacement referring to a capture group was therefore silently wrong in one direction or the other — a Go-style `${1}W` came out as the literal text `${1}W`, and a Python-style `\1` substituted where go-cty would have emitted it verbatim. Confirmed against the oracle in both directions and pinned by a 612-case differential sweep.
  10. **`values` returns a map's values in key order, and both `keys` and `values` return a tuple for an object.** `values` used insertion order while `keys` sorted, so the two no longer corresponded and `zipmap(keys(m), values(m))` — the ordinary way to rebuild a map — silently paired every value with the wrong key. The object result type also changed: go-cty returns a tuple, since an object's attributes have differing types and a list would widen them all to dynamic. No caller anywhere in the workspace, and neither is a registered provider function.
  11. **`formatdate` uses go-cty's format dialect, not Go's layout strings.** This is the widest of the thirteen. The old implementation translated Go's own `2006-01-02` reference layout into `strftime`; go-cty defines its own scheme — `YYYY`, `MM`, `DD`, `EEEE`, `hh`, `AA`, `ZZZZZ`, with `'...'` quoting literals — and reads digits as literal text. So `formatdate("2006-01-02", ts)` now returns the string `2006-01-02` rather than a formatted date, and `formatdate("YYYY-MM-DD", ts)`, which used to pass through unchanged, now works. Both directions fail silently: the old dialect still returns *a* string. Every call site needs rewriting.
  12. **`formatdate` and `timeadd` parse RFC3339 strictly**, where they used `datetime.fromisoformat` and so accepted a bare date, a space in place of the `T`, a lowercase `t` or `z`, and an offset without its colon. go-cty carries its own RFC3339 parser precisely so this does not vary with the host language. `timeadd` also renders a zero offset as `Z` rather than `+00:00` — same instant, different string, and Terraform compares strings.
  13. **`jsondecode`, `csvdecode` and `merge` return concrete types.** `jsondecode` gave a `dynamic` wrapper; it now returns the type the document implies, which for a JSON array is a **tuple**, not a list. `csvdecode` returns `list(object(...))` with every column a string, and now refuses a missing header line, a duplicate column name, or a ragged row, all of which it used to accept. `merge` keeps the argument type when the arguments all share one — so merging maps yields a map instead of an object — and returns an empty object for no arguments. The decoders' types cross the wire, so this is what Terraform sees.
  14. **A null is accepted inside a `CtyList` and for any object attribute.** Both were invented rules with no counterpart in go-cty, and both refused on *read*, so state go-cty had written could not be decoded. The break is not the acceptance — that is a widening — it is that **`CtyObject.validate` no longer checks required-ness at all**, because it never had the information to: a `CtyObject` records optionality, which is a wire-format concern, not intent. Anything relying on cty to enforce "this attribute must be supplied" has to do that itself now. Inside this workspace that is `PvsSchema.validate_config`, which does as of `pyvider` `5fb7b13`; outside it, any provider validating through a bare `CtyObject` silently stops being told. This one belongs *with* the pyvider release rather than merely before it.
  15. **Strings are measured in grapheme clusters, not code points**, in `strlen` (new), `strrev`, `substr` and `format`'s width and precision. Two of those were corrupting rather than miscounting: `strrev` reversed *inside* a ZWJ emoji sequence and produced a different emoji, and `substr` returned fragments of a cluster — a bare zero-width joiner where go-cty returns the next character. Any caller relying on code-point indexing gets different answers, which is the point.
  16. **`substr` accepts what go-cty accepts, and `format`'s `%q` stops escaping non-ASCII.** A negative offset counts back from the end and any negative length means "the rest"; both were refused outright. `%q` emitted `\uXXXX` for every non-ASCII character because `json.dumps` defaults to `ensure_ascii=True`, where Go's `%q` keeps a printable rune as itself.
  17. **`cty_from_json` reads what go-cty reads, which is both stricter and looser than before.** An attribute the type does not declare is now an **error** where the document's extra key was silently dropped; an attribute the document omits is now **null** where it was refused. A JSON number for a string-typed position is accepted and yields the literal digits (`1.50` → `"1.50"`), as are a bool for a string and a string for a number or bool. A decoder that refuses what the reference accepts rejects ordinary state files, and one that drops what it does not recognise turns a typo into "unset".
  18. **`cty_to_json` escapes `<`, `>` and `&`** as Go's encoder does, and converts a non-conformant value before serializing, as go-cty documents. The escaping changes the *bytes* of every document containing one of those characters — no value changes, but Terraform compares state textually.
  19. **`value_range().includes()` no longer answers `True`.** It answers false or "cannot say", which is what go-cty answers: a known value's range is synthetic and never concludes membership from bounds. Its undecided answer is now refined not-null, and `value_range()` itself raises on a marked value where it used to answer. Callers testing `.value is True` get an unknown instead; the exclusion half is unchanged.
  20. **A list or a set no longer converts to a tuple.** go-cty has no such conversion -- a collection's length is a property of the value and a tuple's is part of its type -- and `can_convert_unsafe` already denied it, so `convert` was contradicting its own predicate. Anything relying on the positional conversion has to convert to a list, or build the tuple itself.
  21. **A conversion result no longer carries a type constraint.** Converting to an object type with optional attributes produces a value whose type has none, and converting to `list(any)` produces a list of the *source's* element type rather than `list(dynamic)`. Both are go-cty's behaviour and both change what a provider puts on the wire. Widening in the same change, and so not breaking: a map now converts to an object, which was refused outright.
  22. **A traversal visits a map's keys and an object's attributes in sorted order.** `walk`, `deep_values` and `transform` used insertion order for a map and declaration order for an object, both of which are properties of how the value was built rather than of the value. go-cty sorts, "so that results will always be stable given the same input". Anything depending on the old order was depending on which spelling of the type produced the value.
  23. **The wire bytes for an unknown change.** A bare unknown is now the fixext1 `d4 00 00` rather than an empty ext payload, and a refined number bound is encoded as a number rather than as the UTF-8 bytes of its digits. Both decode to the same value in either spelling -- go-cty accepts ours and always did -- so nothing breaks functionally; what changes is the bytes, which is the point, because Terraform compares serialized state.
  24. **A comparison against null can now be decided by a refinement.** An unknown refined as not-null, compared against a null, was undecided and is now false -- go-cty decides this first of all. The undecided answer of `equals` is also refined not-null, so a caller asking whether the answer could be null gets "no" where it used to get "possibly".
  25. **A container holding an unknown element is a *known* container.** `is_unknown` on a partially-unknown list, map, set or tuple flips `True` -> `False`; the old question is `is_wholly_known()`. This is the widest-reaching entry in the list and it is a *fix*: the container previously encoded to the wire as a bare unknown, destroying the known elements and the known length with it. Everything downstream becomes more precise -- `length` answers, `walk` descends, `unknown_as_null` nulls the element rather than the container, and `equals` can decide from an element that already differs. Callers that tested `is_unknown` to mean "is anything in here undecided" must move to `is_wholly_known()`.
  26. **A set's payload is an ordered tuple, not a frozenset**, in go-cty's canonical order. Two unknown elements are no longer de-duplicated into one, because they are not equivalent -- so a set's length can now be larger than it was, and `length` on a set holding an unknown returns a *refined unknown* `[1, n]` rather than a count. Code doing set algebra on `value.value` directly must treat it as a sequence.
  27. **`sort` defers instead of refusing.** A list holding an unknown element now returns a same-length list of unknowns, where it raised `CtyFunctionError`. A *null* element still raises.
  28. **Refinements survive `validate` and the decoder.** A refined unknown keeps its refinement when placed in a container and when decoded from msgpack; both previously flattened it to a bare unknown. The wire bytes change accordingly -- ext 12 where there used to be `d4 00 00` -- which is again what Terraform compares.

  29. **Argument errors come from the framework, in go-cty's wording.** A wrong type is `number required, but received string` (previously per-function prose); a null is `<func>: argument N must not be null`. Both are `CtyArgumentError`, a `CtyFunctionError` subclass carrying the zero-based `index` — existing `except CtyFunctionError` handlers keep working. And ~35 functions that returned *unknown* for a null argument now refuse it, which go-cty's parameters demanded all along.
  30. **Unknown answers are typed and refined.** `upper(unknown)` is an unknown *string* refined not-null, not a bare unknown dynamic — go-cty's stdlib carries 75 `RefineResult`s and this package carried none. First measurement: 470 of 542 argument positions disagreed on the unknown answer; now 0. The wire bytes change (ext 12 where there was `d4 00 00`), which is what Terraform compares. `strlen` also derives a length lower bound from a refined input's known string prefix, and `length(unknown collection)` answers `[0, 2^63-1]` (or the input's own bounds).
  31. **`max`/`min` are numbers-only and no longer narrow from refinement bounds.** `max("z", "a")` is refused (go-cty's parameter is `cty.Number`), and `max(unknown < 10, 20)` is *unknown* — the old `20` was sound, but go-cty's parameters never admit the unknown to the implementation, so the bound arithmetic never runs. A deliberate precision loss for byte parity; go-cty puts that arithmetic on `Value`'s operators, a surface this package does not have.
  32. **The four ordering comparisons refuse strings and nulls.** `lessthan("a", "b")` type-checked and answered; go-cty's `Value.LessThan` is defined on numbers. Their bound-aware answers on *refined unknowns* are kept — go-cty consults ranges there.
  33. **`coalesce` stops at the first unknown, unifies its return type, and refuses all-null.** It skipped unknowns (a definite answer a later apply could contradict), returned the winning argument unconverted, and returned null for all-null where go-cty errors `no non-null arguments`. `coalesce(1, "b")` is now the string `"1"`.
  34. **`zipmap` refuses what it used to truncate, and returns an object for tuple values.** Mismatched key/value lengths silently dropped entries; go-cty errors in both `Type` and `Impl`. With `list(tuple)` values the result is an object (one attribute per key), not `map(dynamic)`. Keys are declared `list(string)`, so container keys are refused at type-check instead of landing as a Python `repr`.

  36. **`lookup` converts the default to the map's element type** and refuses one that will not convert — `lookup(map(string), k, 5)` answers `"5"` where it used to answer `5`.
  37. **`hasindex`/`index` accept list, map and tuple only** (sets and objects were accepted before), `index` predicts its element type, and a tuple index is range-checked at type-check.
  38. **Numeric edge semantics are go-cty's.** `divide(x, 0)` is signed infinity (`0/0` and `Inf/Inf` error); `modulo(x, 0)` is `x`; `modulo(Inf, y)` is `Inf`; `modulo` computes exactly (was `float64` `fmod`); `multiply(0, unknown)` is unknown (was known `0`); `log`'s edge values return infinities where they refused; `pow(0, 0)` is `1`; `signum` refuses a fraction; `parseint` takes bases 2-62, uses Go's `big.Int.SetString` grammar (no whitespace, `_`, or `0x`), and *errors* on an unparseable string where it returned null; `int`/`ceil`/`floor` handle infinities instead of raising `OverflowError`.
  39. **String semantics are Go's, not Python's.** `upper`/`lower` use UnicodeData's simple per-rune mapping — `upper("straße")` is `"STRAßE"` not `"STRASSE"`, `lower("ΣΣ")` is `"σσ"` not `"σς"` (no final-sigma rule), verified equal to Go at all 1,114,112 code points. `title` replaces one letter per word without lowercasing the rest. `chomp` removes *all* trailing line breaks. `trimsuffix` with an empty suffix returns the string (it deleted all of it). `trimspace` trims Unicode `White_Space` only (Python also stripped the ASCII information separators). `substr` refuses a fractional index it used to truncate. `split("", s)` splits per character instead of raising a bare `ValueError`. `join` is variadic, refuses a tuple, and errors on a null element it used to render as `"None"`.

Containers now hash by their canonical sort key; a capsule with no `hash_fn` hashes per-type, as go-cty's sets do. `_equals_set` matches go-cty 13-for-13 on the oracle (it was 4-for-13 plus crashes): only *top-level* unknown elements defer, so two sets each holding a nested unknown but differing in a known part now answer `false`, not unknown. With hash bucketing, equal 1000-element sets compare in 13 ms, down from 1295.
  42. **`distinct` de-duplicates container elements** it used to refuse as "not hashable" — go-cty compares with three-valued `Equal` and has no such refusal.

### 1. When does #12 (function framework) land?

Real rework tension. If the framework lands *after* #7 and #9, those functions get written hand-rolled and then migrated.

**Current plan:** make #5's decorator the seam. Define the wrapper interface in phase 1, write everything in #7/#9 against it, let #12 fill in behind it in phase 7 without touching function bodies. Correctness lands immediately; rework avoided. Cost: the decorator is slightly over-designed for what phase 1 alone needs.

**Alternative:** do the big refactor up front — moves #12 to phase 3 and delays phases 4–6 by its duration.

**Status:** partly resolved, 2026-08-16. The seam exists and every one of the 79 stdlib functions goes through it: `@stdlib_function("<go-cty name>")` in `functions/_framework.py`, which registers the name and applies the mark policy. Two properties of *being* a stdlib function now live in one place instead of being re-derived per function.

What is still hand-rolled is the argument policy — **146 null/unknown checks across the function modules, no two quite alike**, where go-cty declares each parameter's type and whether it accepts null, unknown or marked values and enforces it before `Impl` runs. Moving it behind the decorator makes the class of bug unrepresentable rather than fixed one at a time.

**Status: resolved, 2026-08-17 — landed, and before 0.5.0.** The full framework port is in (`functions/_function.py`), all 83 functions declare their `Spec` through `@stdlib_function`, the pre-framework path is deleted, and the sub-decision resolved itself the right way round: one breaking release, not two. See the #12 entry in Phase 7 for what the migration and its adversarial review found.

### 3. Numeric precision model

Found by the stdlib sweep, and it differs in *both* directions.

go-cty holds a number in a 512-bit `big.Float`, so `divide(1, 3)` comes back with 155 significant digits against this package's 28 (Decimal's default context). But its transcendental functions compute in `float64` first, so `pow(2, 0.5)` comes back with 17 significant digits, and there this package is the **more** accurate of the two.

Neither is a wrong answer. Matching go-cty means both widening the Decimal context *and* deliberately reproducing its float64 rounding step in `pow` and `log` — that is, making the implementation less accurate on purpose so that a value round-trips identically. That is a decision about what parity means here, not a bug fix.

Terraform compares values as they arrive on the wire, so a difference in the last digits is a real diff, not a cosmetic one.

**Measured against real Terraform, 2026-08-17** — and the measurement changes the shape of the decision, because it shows the divergence is user-visible in *both* directions:

| `1/3` | digits |
|---|---|
| `terraform console` | `0.3333…335`, **155** |
| `soup-go` / go-cty | `0.3333…335`, **155** — byte-identical to Terraform |
| pyvider-cty | `0.3333…333`, **28** |

and `pow(2, 0.5)`: Terraform answers `1.4142135623730951` (float64, 17 digits), pyvider-cty answered `1.414213562373095048801688724` (28). So "this package is the more accurate one" is true and *does not help* — more accurate than Terraform is still different from Terraform. **This row is what settled `pow`; see the split below. Since 2026-08-18 this package answers `1.4142135623730951` too.**

**Widening the Decimal context does not fix it, and the trailing digits are the proof.** go-cty's answer ends `…335` because it is a 512-bit *binary* float printed exactly; a decimal division at any precision ends `…333`. The two round on different lattices, so parity here is not a precision setting — it is a representation change.

**Split 2026-08-18: `pow` and `log` are settled, `divide` is still the open question.** The recommendation below was written as one decision covering all three, and the measurement directly above it is what pulled them apart. It is quoted unchanged; read it as being about `divide`.

`log` was already transcribed through `float64`, and `pow` joined it (`d8ec5a2`). Not on the digits argument — on three answers that were not digits at all. go-cty's `PowFunc` reads both arguments with `gocty.FromCtyValue` into a `float64` and returns `NumberFloatVal(math.Pow(...))`, so `Decimal` was not a more precise version of that function, it was a different one: `pow(10, 1000000)` raised `decimal.Overflow` where go-cty answers `+Inf`, `pow(10, 400)` answered exactly `1e400` where go-cty answers `+Inf`, and `pow(1e400, 2)` never made the float64-range refusal that `log` makes on the identical input. None of those is a last-digit question, and the first is a crash outside the error taxonomy.

This costs no dependency and no representation change — the two things that make the `divide` case expensive. What it does cost is honesty about two residues, both now strict xfails: a number this package computes in `float64` reaches the wire as text where go-cty writes a `float64`, because a `Decimal` does not record that it came from one; and Go's `math.Pow` is not correctly rounded where the platform libm behind Python's is, putting them three ULPs apart at `pow(10, 308)`. **Flagged for Tim:** this moved past a recommendation that was recorded and awaiting him. The argument is above; reverting it is one commit.

**Recommendation (2026-08-17, and now read as being about `divide`): keep Decimal, document the boundary exactly, and do not degrade `pow`/`log`.** The reasoning is about blast radius. Numbers that *arrive* from Terraform round-trip byte-identically today — the codec tests pin that — so the divergence exists only for numbers this library **computes**. A provider that echoes config values, which is what providers overwhelmingly do, never meets it. Meeting it requires the provider and Terraform to compute the *same expression* on the same inputs and then compare, which is a narrow shape and a knowable one.

The alternative — matching exactly — means adopting a 512-bit binary float (mpmath or gmpy2) as the number representation, reimplementing Go's `Text('f', -1)` shortest-round-trip formatting, **and** deliberately routing `pow`/`log` through float64 to reproduce go-cty's precision loss. That is a new dependency, a rewrite of the most-used value type, and a permanent commitment to being less accurate on purpose. It buys correctness in a case that can be avoided by documentation. Worth doing only if a real provider is ever bitten.

**What to do now, cheaply:** state the boundary in the numeric docs with these measured figures, and keep the two strict xfails — they are the living record, and they will fail the moment anyone changes the arithmetic in either direction.

**Status:** `pow`/`log` decided 2026-08-18 and implemented, for reasons that turned out not to be about precision. `divide` unchanged: recommendation recorded 2026-08-17, awaiting Tim. All three are held as strict xfails in the sweep so they stay visible.

### 4. Null arguments: raise or return unknown?

go-cty refuses a null for any parameter not declared `AllowNull`, and none of the stdlib's are. This package mostly returns unknown instead. The nine functions added on 2026-08-16 follow go-cty and raise, so the package currently has both conventions.

Deliberate, and recorded rather than papered over: the new functions have no callers, so following go-cty from the start costs nothing, while converting the other ~70 is a behavioural break for every one of them.

**Impact:** settling it is one declaration per parameter *if* the function framework lands first, and ~70 individual edits if it does not. That is the real argument for sequencing the framework before 0.5.0.

**Status: resolved, 2026-08-17, by decision 1 landing.** Every parameter now declares go-cty's own `AllowNull` — transcribed from its `Spec`s, not guessed — and the framework refuses the rest before the implementation runs, with the position on the exception. The 2026-08-16 measurement (109 of 138 positions disagreeing) is now 0, held by the sweep's nulled-argument population.

### 2. Unicode segmentation dependency (gates phase 3 item 2)

`Strlen` and `SafeKnownPrefix` need real UAX#29 grapheme cluster segmentation. go-cty tracks Unicode 17 on Go 1.27+, Unicode 15 below.

Options: take a dependency (`uniseg`-equivalent), vendor the tables, or document an explicit deviation and use code points.

This is a question about pyvider-cty's dependency posture more than a technical one. Gates `strlen` (#9) and `StringPrefix` (#10).

**Status:** **decided and done, 2026-08-16 — vendor. `7d939f8`.**

The framing above was wrong in the way that mattered, and finding out is the argument for never filing from a reading. "Gates `strlen` and `SafeKnownPrefix`" made this sound like *unbuilt* work waiting on a decision. Running the oracle showed go-cty calls `ScanGraphemeClusters` in **four** places — `string.go:69` (`reverse`), `:119` (`strlen`), `:193`/`:217` (`substr`), and `format.go:469`/`:500` — so `strrev` and `substr` were **shipped and wrong**, and not by a count: `strrev` reversed inside a ZWJ sequence and produced a different emoji, `substr` returned a bare joiner where go-cty returns the next character. Deferring was deferring a live bug.

**Why the sweep never caught it.** Its Unicode cases were `héllo` and `école`, which NFC-compose to one code point per character. 1:1 grapheme-to-code-point, so they pass under either implementation — coverage that reads as Unicode coverage and tests nothing about segmentation. This is the fourth instance of the same shape and the most expensive.

**The choice, and how the reasoning moved.** Four options were costed: vendor from the UCD, depend on `regex`, depend on `uniseg`, or decline. The first recommendation was to write a state machine from scratch, justified by pinning the Unicode version exactly. **That collapsed on reading `cty/internal/graphemes`**, which is a one-function shim selecting `go-textseg` v15 or v17 *by Go toolchain version* — go-cty does not pin its own, so there is no exactness available to match. The second recommendation was `uniseg`, until measurement: its wheel is 8 MB, of which **10.2 MB uncompressed is bundled Sphinx docs and webfonts**, for 262 KB of code — under the library all ten repos sit on.

What settled it was measuring separability instead of assuming it. Grapheme clustering needs **3 of uniseg's 30 property columns**; reprojecting collapses 251 table rows to 18 and compresses to 1.5 KB, so the vendored table is **4.4 KB**. MIT, so the lift is permitted; attributed per-file per REUSE with `LICENSES/MIT.txt`. Verified equal to uniseg's at all 1,114,112 code points, and the ported rules verified against uniseg over 212,696 strings.

**The residue, which is real and self-resolving.** The oracle is built with go1.26, taking the `!go1.27` branch and therefore Unicode 15.0, which predates GB9c — so it reads `क्ष` as two characters where 15.1 onwards read one. Not matched: 15.0 is the outlier and go-cty already carries the v17 that agrees with us. Four strict xfails, so rebuilding the oracle on go1.27 turns them XPASS and forces them out.

### 5. Should CI run the differential suite? — **resolved 2026-08-17: yes, and it does**

The entire oracle suite was developer-local. `.github/workflows/ci.yml` delegated to `provide-io/ci-tooling`'s shared Python workflow with no Go setup, and the `compat` marker is skipped without `--run-compat` — so every divergence this branch found was caught only because someone ran `make compat` at a keyboard. The guards added the same day (behaviour probes, hard-fail on a stale or unbuildable harness) protect the *local* run's honesty; they cannot make the run happen.

A second job now does. `tofusoup` is public, so the cross-repo checkout needs no token; the harness pins go-cty itself, so the reference version is soup-go's `go.mod` rather than anything chosen in the workflow; and `make compat` rebuilds from source every run, which is the property that matters most (a cached binary is how this suite once spent a day measuring against a harness that predated most of what it was checking). `scripts/compat/run_compat.py` gained a `SOUP_GO_SRC` override so the sibling-checkout assumption is a default rather than a requirement — the same fault class as the hardcoded path fixed in `pyvider`'s `audit_pins.py`.

**The Go pin is load-bearing, and this is the part to remember.** go-cty selects `go-textseg` v15 below Go 1.27 and v17 at or above it — two different Unicode versions. The four GB9c cases are **strict** xfails against the v15 answer, so a toolchain bump to 1.27 turns them XPASS and fails the suite. The workflow pins Go 1.26 and says why; when the bump comes, the fix is to delete those four entries from `KNOWN_DIVERGENCES`, not to widen the pin. This is the first thing in this repository whose correctness depends on a toolchain version, so it is worth stating twice.

**One sequencing constraint, for the release wave.** The job checks out `tofusoup`'s default branch. The harness fixes from the 2026-08-17 audit (`65f134c`, `8e0ce04`) are on `chore/suite-dependency-refresh` and unpushed, as is this branch. So the job is only as correct as what has landed on `tofusoup` main — **tofusoup's harness fixes must merge at or before this branch does**, joining `pyvider` in the wave ordering below.

### Replacing `datetime` — measured, and the year range is the least of it

Asked on 2026-08-18: what would it buy beyond the extended year range? Three
candidates, and only two survive contact with the oracle.

**1. The calendar range — real.** `datetime` caps at years 1-9999; Go's
`time.Time` runs to 292277026596. This is the `timeadd` divergence above.

**2. Nanosecond resolution — real, and far narrower than it sounds.** `datetime`
resolves to microseconds and Go keeps nanoseconds, but **neither implementation
can ever render sub-second precision**: go-cty's `formatdate` verb set stops at
`s`/`ss`, and both write RFC3339 without a fractional part. So the difference
only escapes at a *carry* boundary — 7-9 fractional digits, plus a
sub-microsecond duration, plus a rollover:

    2026-01-01T00:00:00.999999999Z + 1ns   go-cty 00:00:01Z   this 00:00:00Z
    2026-01-01T00:00:00.123456789Z + 1s    both   00:00:01Z   (agree)

**3. Duration range — not a benefit; already correct.** Go's `time.Duration` is
int64 nanoseconds (±292 years) and this package's parser enforces the same
limit rather than inheriting `timedelta`'s much wider one. The cutoff matches
exactly: both accept `2560000h`, both refuse `2570000h`. Pinned in the sweep so
a rewrite cannot lose it.

**What the replacement looks like**, confined to `datetime_functions.py`:
represent an instant as an integer nanosecond count plus civil-calendar
conversion (`days_from_civil` / `civil_from_days`, ~8 and ~10 lines, proleptic
Gregorian and no leap seconds, which is exactly Go's model); stop converting the
duration to a `timedelta` at the end of `_parse_duration`, since it is already
integer nanoseconds; make addition integer addition; render nanos -> civil. The
RFC3339 grammar, the duration grammar and the verb dispatch all stay. Roughly
120-150 lines. No timezone database is needed — RFC3339 carries fixed offsets
only.

**Risks if it is ever done:** calendar math is easy to get subtly wrong and
needs a differential sweep over a wide date range, and `datetime`'s free
validation of month 13 / day 32 would have to be reimplemented.

**Decision: not for 0.5.0.** Both reachable benefits need inputs Terraform
cannot produce.

### Will not be fixed

- **`pow`'s last ULP.** Go's `math.Pow` is not correctly rounded; the platform libm behind Python's is. Reproducing Go's rounding error is not parity worth having.
- **The float64 wire spelling.** Recording that a number came from a `float64` is a change to how every number is stored, and the naive version is the bug `codec.py:296` exists to prevent.
- **`divide`'s precision.** Needs a 512-bit binary float as the number representation. See decision 3.

`test_validate_preserves_marks.py` (540), `test_numeric_functions.py` (503),
`test_conversion_oracle.py` (503). No gate in this repository enforces a cap.
